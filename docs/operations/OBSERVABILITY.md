# Observability: logs, events, and metrics

PolyGraph has three distinct observability outputs. They should not be mixed.

## 1. Operational logs

Operational logs answer “what is the program doing now?”. They are human-readable text produced through the logging/spdlog layer.

Default behavior:

- console/stdout sink at `info` and above;
- rotating text file `logs/polygraph.log`;
- debug-level file logging;
- errors flush immediately.

CLI:

```bash
--log-file measurements/run/logs/run.log
# alias: --application-log-file
```

A `.jsonl` or `.ndjson` path is rejected for `--log-file` because operational logging is not JSONL. Use `--event-file` for structured events.

Long loading stages emit progress. Graph/cache loaders and Redis report roughly every five seconds; the GPU runtime reports graph scanning and emits a five-second heartbeat while the cuGraph projection build is running.

## 2. Structured execution events

Events are machine-readable lifecycle/performance records generated by the compile-time event instrumentation. They are independent of normal logging and are emitted as JSONL.

Default file:

```text
logs/polygraph.events.jsonl
```

CLI:

```bash
--event-file measurements/run/events/run.events.jsonl
--event-dir measurements/run/events
--event-name run.events.jsonl
--no-event-log
```

Each line is one JSON object. This is the input consumed by the timeline/log-reconstruction tooling.

The normal wrapper keeps channels separate:

```text
measurements/<run-id>/
  events/<start>/<rep>.events.jsonl
  logs/<start>/<rep>.log
  outputs/<start>/<rep>.csv
  measurements.csv
  summary.json
```

## 3. Metrics

The C++ metrics subsystem exposes resource/runtime measurements through the configured metrics endpoint. Collectors include process memory/CPU, jemalloc or glibc allocator statistics, GPU/NVML metrics, HTTP metrics, and projection statistics where enabled.

The repository observability stack uses Prometheus for scraping, Grafana for dashboards, cAdvisor for container-level resource metrics, and Loki/Alloy for log aggregation where configured.

See `config/observability/observability.json` for collector enablement, TTLs, sink levels, queue sizes, and metric selection.

## Reconstruction

To reconstruct event spans/timelines:

```bash
python3 tools/polygraph.py analyze-logs measurements/<run-id>/events \
  --out-dir measurements/<run-id>/reconstructed
```

For a live timeline server:

```bash
python3 tools/polygraph.py live-logs \
  --watch-dir measurements/<run-id>/events
```

Only `*.events.jsonl` should be passed to reconstruction. Human-readable `.log` files are intentionally not valid reconstruction input.

## Failure logging

A BFS failure is represented twice for different consumers:

- human operational log, e.g. `BFS CLI failed: ...` in stdout and `.log`;
- structured event `bfs.cli.failed` in the `.events.jsonl` file.

This separation prevents text such as timestamps, `[error]`, and comma-separated fields from being mislabeled as JSONL.
